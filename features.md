# QUIC Migration Feature Summary

Now that we have a way to generate fingerprints and capture them, we need a way to represent it in a form which is understood by a model, but also we have to pay attention to what kind of features we are extracting from the fingerprints, as a lot depends on the dataset.

We were checking out already existing Network Traffic Datasets to get an idea on what type of features are usually extracted, then we used this knowledge to come up with a proposal for our dataset and an initial methodology we will use to generate the synthetic data. We would like to hear your feedback, as we are not sure this is the best way to do it, and also we have a few questions. 

One of the biggest sources for our inspiration was this article, and how they constructed their dataset, with the exception that their data is not decrypted: https://www.sciencedirect.com/science/article/pii/S2352340923000069.

## 1. Proposed Hierarchical Solution

### Stage 1: High-level features with CTGAN and Diffusion models

So first we would create one training dataset, which consists of *high-level features*(metadata) for each fingerprint (network traffic flow). In the .csv file each row would represent one fingerprint. We would be using this training data to generate the flow-specific information, using the GAN architectures and Diffusion models we did our research on. This would be the first step of a hierarhical approach. 

* Output:  A single synthetic row of metadata. For example:
[migration_type='ACTIVE_MIGRATION', handshake_duration=0.2, total_http_streams=5, ...]
This vector would be the conditioning vector for Stage 2.

### Stage 2: Low-level features - sequence generation

The next step would be to generate the data for the individual packets. As we see it, the packets are dependent on each other, so we have to use a model, that is able to handle sequential data, perhaps TimeGAN or RGAN, but we would have to look more into this topic. The training data for this stage would consist of the sequence of per-packet feature vectors, and of course we would use the output of Stage 1, as the condition to generate the packet data in this step.

* Output: A sequence of vectors, where each vector represents a packet. For example:
[[pkt1_features], [pkt2_features], [pkt3_features], ...]


### Stage 3: Ensuring Protocol Correctness.

 In this step we were thinking of using mainly rule based algorithms, refining the previously generated fingerprint metadata, and lower packet data, as we would want to ensure the protocol correctness in our dataset. The reason for this is that there a lot of rules, which have to be correct in order to be able to consider the fingerprint realistic, e.g. the values of the Connection IDs have to be either the initial values, or the ones sent in a NEW_CONNECTION_ID packet, or when the server sends a Retry pcket, the retry_source_connection_id transport parameter has to from the server after receiving a Retry packet, otherwise there should be a TRANSPORT_PARAMETER_ERROR (https://www.rfc-editor.org/rfc/rfc9000.html#section-7.3-5). We assume these small details should be followed in our dataset, if we want to make it realistic, although this is complicated mostly for the decrypted dataset. For the encrypted dataset we won't be seeing this much detail anyways. 

We  would add the IPs, and CIDs here also, which dont have to be generated by the models.

 * Output: We don't know if the output synthetic data should be a .pcap file, which for now seems a bit complicated to us, or we just define some other format for the output data.

This is a two-stage process:
* Stage 1: Generation Stage (The GAN): The GAN's job is to learn the statistical blueprint of a migration event. It takes feature vectors and learns the patterns and correlations. Its output is a new, synthetic feature vector that is statistically similar to the real ones.
* Stage 2: Reconstruction Stage (A Rule-Based Script): a separate, programmatic script that takes the synthetic feature vector from the GAN as input and uses it as a set of instructions to build the actual sequence of packets, following the protocols rules ensuring correctness.

- **GAN** learns *statistical fingerprints* of QUIC migration events (feature vectors).  
- **Reconstruction script** converts synthetic vectors to valid QUIC packet sequences (`.pcap`).  

- Two-stage approach ensures:  
  - Realistic variability (via GAN).  
  - Protocol correctness (via scripted logic).

### 2.3 Features for GAN Training

#### 1. Temporal & Latency
- `time_until_migration` (num) → Time from connection start to migration.  
- `challenge_response_latency` (num) → Delay between PATH_CHALLENGE and PATH_RESPONSE.  
- `post_migration_first_ack_delay` (num) → Delay to first ACK after migration.  

#### 2. Path & Size
- `challenge_packet_size` (num) → Size of PATH_CHALLENGE.  
- `response_packet_size` (num) → Size of PATH_RESPONSE.  
- `padding_used_on_challenge` (bin) → Whether challenge was padded (MTU probing).  
- `ip_version_change` (cat) → E.g., IPv4→IPv6.  
- `port_change` (bin) → Whether client source port changed.  

#### 3. Protocol Behavior
- `new_connection_id_issued` (bin) → If NEW_CONNECTION_ID frame was sent.  
- `packets_on_old_path` (num) → Count of packets before migration.  
- `packets_on_new_path_before_challenge` (num) → Packets sent before validation.  


### 2.4 Workflow

1. **Data Preparation**  
   - Parse QUIC captures.  
   - Identify migration events (4-tuple change + PATH_CHALLENGE/RESPONSE).  
   - Extract fixed-size vectors using the above features.  

   Example row:  
[12.3, 0.08, 0.03, 1350, 1350, 1, 0, 1, 1, 58, 2]

2. **GAN Training**  
- Input/Output: feature vectors.  
- Generator produces synthetic migration fingerprints.  
- Discriminator enforces realism.  

3. **Reconstruction Script**  
- Reads synthetic vector → builds QUIC migration:  
  - Pre-migration traffic.  
  - Path change (new IP/port, same CID).  
  - PATH_CHALLENGE/RESPONSE exchange.  
  - Post-migration stabilization traffic.  
- Output: `.pcap`.
